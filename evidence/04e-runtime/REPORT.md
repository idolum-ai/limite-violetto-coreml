# Experimental prediction GIL release

The candidate-4 partition audit stalled in a lock cycle, distinct from ordinary long Core ML computation. In the [first stack sample](../04d-audit/candidate4-partitions/wait-sample.txt), the Python prediction thread spent all 770 samples in Core ML `MLE5ExecutionStreamPool takeOut` → `cancelPendingReset` → synchronous wait for a serial reset queue. Multiple reset-queue workers spent all 770 samples in input-port reset → `MLFeatureValue dealloc` → the installed `guarded_destruct` → `PyGILState_Ensure` → `take_gil`. An independently captured [second sample](../04d-gpu/stall-second-sample.txt) at 19:24:18, about one minute later, showed the same stacks for all 2,315 samples. No sampled thread made forward progress.

The retained Core ML Tools 9.0 [binding source](../../sources/coremltools-9.0-bridge/CoreMLPython.mm) binds `.def("predict", &Model::predict)` without a GIL-release call guard. `Model::predict` constructs the input features, then calls synchronous `[m_model predictionFromFeatures:usingState:error:]` while pybind holds the Python GIL. The installed cleanup guard correctly acquires the GIL before destroying the input `py::array` on a Core ML reset worker. Thus the prediction thread holds the GIL while waiting for the reset queue, and the reset worker holds that queue while waiting for the GIL. The sampled stacks plus retained binding source establish the cycle; the precise trigger is Core ML's lingering stream reset after prior predictions.

The isolated [native prototype](../../coreml_port/native/prediction_guard.mm) process-locally swizzles the public `MLModel` `predictionFromFeatures:error:` and `predictionFromFeatures:usingState:error:` methods. It releases the GIL only while the original synchronous Core ML method runs, then restores it before control returns to the pybind bridge; C++ RAII and Objective-C `@finally` cover normal return and exception unwinding. Calls from threads that do not hold the GIL pass through unchanged. Installation checks method argument counts, object return types, and Core ML implementation provenance before swizzling. It does not alter the installed wheel, OS framework, cleanup guard, model packages, or runtime selection. [Build record](prediction-guard-build.json) captures source and dylib SHA256 hashes.

The bounded [synthetic probe](prediction-guard-synthetic.json) runs its two modes in disposable child processes through `ctypes.PyDLL`, which retains the GIL on C entry. The simulated synchronous Core ML call dispatches a worker that must acquire the GIL before it can signal completion. The unguarded child timed out after three seconds and was killed by the probe; the guarded child completed with exit 0. A fresh interpreter installed the existing cleanup guard first, then `violetto_install_prediction_guard()` returned 0. These tests prove the proposed release scope breaks the reproduced lock cycle and that the swizzle can install on this host. They do not yet prove actual Core ML predictions intercept these methods, preserve numerical outputs, or survive repeated idle/reset use. An actual one-shard stress and numerical identity test is required before any runtime wiring.
