# Raw key and RoPE tap extension

The first four-tap replay passed every within-policy control. On the failed 44-token prompt, the cold 32-token chunk matched at rounded normalized input `x_5` but differed by rounded key projection `value_5`; the warm 12-token chunk matched through rounded key normalization `k_7` but differed at final rounded key `k_9`. This separate source clone adds existing raw values to bracket those intervals. It does not revise the qualified model, the first tap clone, or their replay evidence.

The ordered tap set is `x_5` (535), raw key projection `x_9` (1141), `value_5` (1169), `k_7` (1592), raw cosine product `x_27` (1680), rounded cosine product `var_2083` (1706), raw sine product `x_29` (1713), rounded sine product `var_2106` (1739), raw RoPE sum `x_31` (1740), final-round scale `step_23` (1763), scaled quotient `var_2121` (1764), rounded quotient `var_2122` (1765), and `k_9` (1766). All are original FP32 MIL SSA values. `x_9` has shape `[1,Q,256]`; the RoPE values have `[1,Q,2,128]`; dynamic `Q` is 1–32. The builder pins operation indices/types, shapes, ordered dependencies, and the final `k_9` cache-write path.

`scripts/build_gpu_raw_key_taps.py` copies sealed candidate-6 group 0 into a fresh `raw-key-taps-1` attempt, appends only these values to block and description outputs, and optionally compiles after installing the prediction guard. Every original operation byte, original endpoint, state descriptor, weight, and other spec field must remain unchanged. The output descriptors use FP32, default `Q=3`, and the source input's `Q=1..32` range. Inventories, source identity, script/design snapshots, and deterministic operation digests are recorded.

The separate replay worker will repeat the same eight saved-input/state calls as the first four-tap replay. Raw tap comparisons are diagnostic only if original-vs-instrumented `y`, `tap23_out`, and all eight post-call states are byte-exact within **both** compute policies for **both** chunks, and the original calls reproduce pinned factorial outputs/states. `CPU_AND_GPU` remains a compute-policy label rather than proof of GPU execution.
