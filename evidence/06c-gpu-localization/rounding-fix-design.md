# Bounded GPU-policy ties-to-even correction design

## Observed boundary

The saved 13-tap group-0 replay passed original-versus-instrumented endpoint and all-eight-state byte controls for both compute policies and both chunks; its four shared taps also matched the earlier tap clone. On the cold 32-token chunk, normalized input `x_5` and raw key projection `x_9` are byte-exact across policies, while rounded projection `value_5` first differs. On the warm 12-token chunk, `x_5`, `x_9`, `value_5`, `k_7`, raw cosine product `x_27`, and raw sine product `x_29` are exact, while rounded cosine/sine products differ (five and 23 elements). The raw RoPE sum and final quotient/round then diverge. These are policy-level numerical observations under controlled input/cache, not proof of actual GPU execution. The diagnostic arrays are under `raw-key-replay-1`.

An earlier experimental [`gpu_even_round.py`](../../scripts/gpu_even_round.py) replaces `round(z)` with `floor(z)` plus a fractional and parity test. Its GPU-planned composed QKV trial fixed the observed key midpoint, but the uninstrumented four-layer shard still failed its then-current fidelity boundary; [the earlier report](../04d-gpu/REPORT.md) explicitly did not promote it. That candidate also loses the sign of `-0.0`: a read-only Torch check of `Q([-0.0,+0.0])` produced `[-0.0,+0.0]`, while its `Q_even` produced `[+0.0,+0.0]`. This matters here: the captured raw sine product `x_29` contains 5,452 negative zeros across the two chunks and both policies. Do not reuse the old helper unchanged or infer a full-model fix from its isolated key success.

## Candidate arithmetic and operator gate

For the current finite-range quantizer, retain the **same** exponent clamp, power-of-two `step` table, FP32 operands, and final multiply. Replace only the quotient's midpoint decision. With `z=x/step`, let `low=floor(z)`, `fraction=z-low`, `odd=low-2*floor(low/2)`, and `advance=where(fraction==0.5, odd, float(fraction>0.5))`; return `(low+advance)*step`, with an explicit zero-sign preservation branch. The negative-number behavior follows the same rule: at `z=-128.5`, `low=-129` is odd, so advance to the even `-128`; at `z=-127.5`, `low=-128` is even, so stay there. Use Core ML-convertible arithmetic and `where`; an earlier boolean `__or__` expression did not convert. The zero branch must preserve the sign whenever the **reference rounded result is zero**, including negative underflow, not only when input is literal `-0.0`. A candidate such as selecting `x*0.0` for zero results is a testable implementation idea, not an assumed Core ML guarantee.

First qualify a fresh isolated round model against the sealed Torch `graphs.Q`, comparing **FP32 bytes**, not `np.array_equal` alone. Include positive/negative exact ties with even and odd lower neighbors, `nextafter` values on each side of each tie, exponent boundaries, ordinary captured raw `x_9`/`x_27`/`x_29`/`x_31` arrays, positive/negative zero, and finite values that round to signed zero. Check both `CPU_ONLY` and `CPU_AND_GPU`, several dynamic lengths (including 1, 3, 12, 32), and the candidate's Torch output against original Torch. Require no nonfinite model inputs and explicitly report that NaN/±infinity are outside this quantizer's indexed-step contract; do not claim IEEE BF16 behavior over all FP32 values. For the observed key-path captures, nonzero magnitudes span about `5.28e-6` to `45.39`; test beyond those bounds and pin the range actually exercised by the candidate group. The original clamp at `1e-30` means very small finite FP32 values also require separate exact checks if a broader replacement is contemplated.

An isolated model may be scheduled on CPU even under `CPU_AND_GPU`, as happened in the earlier round-tie probe. Therefore, also test the correction in a composed GPU-policy QKV/round graph and record the compute plan as anticipated placement only. The isolated operator passes only if all finite test vectors, including signed zeros, match the original Torch quantizer byte-for-byte under both policies; one favorable midpoint is insufficient.

## Integration gates

Build a **new**, side-by-side group-0 candidate with the explicit rounding expression at the key projection and RoPE cosine, sine, and final-round sites; keep the sealed candidate-6 and promoted CPU conditional packages untouched. A process-local conversion variant is preferable to editing qualified shared math. First require Torch candidate-versus-original group-0 outputs/states exact on the fixed and held-out Q=1–32 inputs and cache states. Then run uninstrumented native group-0 CPU and GPU-policy calls from the saved cold/warm shared input/cache fixtures: CPU must remain byte-exact to the qualified original; GPU-policy key cache, `y`, `tap23_out`, and all eight post-call states must meet the same exact controls against CPU on those fixtures. Repeat at fresh inputs/positions and dynamic boundaries; a tapped diagnostic alone cannot qualify an uninstrumented package because exposing outputs can change optimization.

Only after this bounded group gate should a full side-by-side candidate be built. Preserve all source/compiled identities, state interfaces, guards, and original acceptance thresholds. Require the established full CPU exact score/token and 63-prefix gates to remain unchanged, then run the previously failed GPU-policy full-model prompts and score/hidden-state gates under the original limits. A local group-0 key correction may leave other GPU-policy drift sources; report that outcome without broadening a single midpoint fix into a global GPU fidelity claim. Performance and actual device placement remain separate measurements.
