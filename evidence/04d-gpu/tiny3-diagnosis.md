# Three-token partition failure: first arithmetic site

Fixture `tiny_33[:3]` uses IDs `[87555, 130664, 114854]`. The corrected pure-Torch graph with ordered linear/norm/XSA/softmax and source exponential reproduces the full-candidate-3 hidden failure: final hidden relative RMSE 0.01973445188644 versus the pinned CPU reference. It matches the reference bitwise through layer 31 and first differs at **layer 32**, where 36 BF16 output elements differ. See [full graph and scalar-three ablation](tiny3-scalar-softmax/summary.json) and [per-layer comparison](tiny3-first-layer/summary.json).

Forcing the pinned CPU softmax's three-key scalar sum order, `(exp0+exp1)+exp2`, in every graph layer leaves all group boundaries and final hidden/scores **identical** to the four-lane graph. The source-level tail exception is real but does not cause this fixture's failure. Changing group-8 KV caches from FP16 to FP32 also leaves layers 32–35 identical; see [cache ablation](tiny3-cache-ablation/summary.json).

At layer 32, attention input and q/k/v projections are bitwise equal to the upstream reference. The first BF16 attention difference is exactly one element, token 2/head 6/channel 80: graph 19.375 versus reference 19.5. FP32 scores differ in 21 values (maximum 2.384185791015625e-6), and weights in 28 (maximum 5.364418029785156e-7). See [attention-stage capture](tiny3-attention32/summary.json).

The [Torch geometry ablation](tiny3-shape-ablation/summary.json) holds q/k/v fixed. Native Q3×K3 scores, weights, and rounded attention match the reference. Q3×K2048, Q16×K3 (real queries at the back), Q32×K3, and Q32×K2048 all produce the same 21 differing scores and the one BF16 mismatch. Exact native weights padded to 2048, multiplied by padded values, still produce exact rounded attention; the weighted-value product is not the cause.

An isolated [Core ML CPU q·k operator probe](tiny3-dot-coreml/summary.json) shows that simply cropping to Q3×K3 will not reproduce the upstream score reduction. Exact-shape Core ML scores still differ from upstream einsum in 21 elements (maximum 2.384185791015625e-6). In the [score-effect control](tiny3-coreml-score-effect/summary.json), those Core ML scores alone, passed through Torch's native softmax and value product, recreate the same BF16 failure: native raw 19.437524795532227 rounds to 19.5; Core ML-score raw 19.437496185302734 rounds to 19.375. The midpoint is 19.4375. Thus the remaining correction must address q·k score arithmetic or an equivalent exact compensation; dynamic key/query cropping alone is insufficient.

An [explicit dot-order search](tiny3-dot-orders/summary.json) tested sequential 128-product FP32 accumulation and 2/4/8/16/32/64/128-lane accumulation with linear, reverse, adjacent-tree, and shuffle folds. None matched the 90 native upstream einsum dots bitwise. Sequential accumulation was closest at 22 differing values, the same difference count as the padded Torch/Core ML score geometry. The pinned [LinearAlgebra.cpp](../../../sources/torch-2.7-linear/LinearAlgebra.cpp) lines 1739–1802 selects a batched/per-batch GEMM path, rather than its naive kernel, for Q3×K3 with reduction width 128 because 128×3×3=1152 exceeds the `<400` cutoff. The exact GEMM arithmetic remains under investigation.

An [FP64 oracle and stride check](tiny3-dot-precision/summary.json) rules out simple higher-precision accumulation: summing exact BF16 operand products in FP64 and rounding once to FP32 differs from 42 of the 90 native dots. The source einsum sees q and repeated k as `[1,3,10,128]` contiguous tensors, then operates per head on `[10,3,128]` strides `[128,1280,1]` and `[10,128,3]` strides `[128,1,1280]`. A [raw-layout/Core ML operator probe](tiny3-dot-layouts/summary.json) found that Torch raw-layout einsum, raw-layout batched matmul, and per-head 2D matmul each match native dots bitwise. Core ML's versions do not: raw-layout conversions differ in 43 dots/40 scaled scores, while per-head Core ML differs in 22 dots/21 scaled scores. Reversing KQ also fails. The source layout affects Torch's selected GEMM path, but tracing that layout into Core ML does not preserve its arithmetic.

Exact raw score identity is unnecessary for this fixture's BF16 boundary. A [causal output check](tiny3-score-candidates/summary.json) feeds each Core ML score tensor through the **same native Torch softmax and value product**, comparing all 3×10×128 rounded attention values. Raw-layout Core ML einsum/matmul and reversed KQ each yield **zero BF16 differences**, although their scores differ in 40 FP32 elements. At the prior failing element, raw-layout Core ML produces 19.437511444091797, just above the 19.4375 BF16 midpoint, so it rounds correctly to 19.5. Per-head Core ML retains the one BF16 failure. FP64 accumulation variants also produce zero BF16 differences. Complete reusable dot, score, weight, raw, and rounded arrays are in [arrays.npz](tiny3-score-candidates/arrays.npz). Raw-layout attention is therefore a candidate correction for this case, pending a composed graph and wider gate.

The [actual padded-geometry test](tiny3-raw-padded-dot/summary.json) narrows that candidate: with K2048 fixed, Core ML **Q3** raw-layout einsum or matmul yields zero BF16 attention differences across the same 3840 elements, despite 38 FP32 score differences. Core ML **Q32** raw-layout einsum or matmul retains the one failing BF16 element. The Q3 result therefore requires dynamic query-row count as well as raw-layout score expression, but does not require dynamically cropped K for this fixture. Its complete score/weight/output tensors are in [arrays.npz](tiny3-raw-padded-dot/arrays.npz). The unconverted Torch Q3×K2048 expression still differs, so only a composed Core ML gate can validate this compiler-dependent option.

That composed gate now passes for the tiny3 fixture. An owned [runtime-row implementation](../../scripts/gpu_dynamic_raw_attention.py) computes front-padded `Q_rows = min(32, last_absolute_position+1)`, keeps all 2048 key slots, and uses raw-layout einsum for the scores. Its [one-layer Core ML package](tiny3-dynamic-layer32/summary.json) receives exact native layer-32 attention input/residual/q/k/v and produces bitwise-exact weighted attention and final layer-32 hidden state. The [uninstrumented four-layer group-8 package](tiny3-dynamic-group8/summary.json) receives an exact Torch groups-0–7 prefix (layer-31 hidden bitwise exact) and returns bitwise-exact layer-35 `y` and tap23. On the **same input**, candidate 3 group 8 differs in 789 elements, maximum absolute difference 80; the experimental expression evaluated in Torch also differs in 789, so this is specifically a Core ML compiled arithmetic result. Runtime-position slicing converted successfully with sequence `RangeDim(1,32)`. This validates one isolated group on one prefix, not decoding or full-model behavior.

These are local CPU diagnostics for one three-token fixture, not a full candidate correction. No shared math or acceptance files were changed. Scripts and package/source hashes are recorded in each linked JSON result.
