# Long-prefix layer-34 attention divergence

The first Core ML BF16 divergence in the saved 1024:1026 replay of group 8 is the weighted-attention rounding site in layer 34. Core ML emits `8.875` at `[batch 0, query 1, head 9, channel 26]`; native Torch emits `8.8125`. Earlier 81 rounding sites are exact. The replay uses the actual saved Core ML cache state, and the corrected Torch group reproduces the native group output exactly. See the [root stage result](../../04d-cpu/long-group8-stages/results.json) and [saved input/state](../../04d-cpu/long-group-locator/).

The [isolated operator replay](summary.json) identifies the weighted-value matrix multiply as the causal operation. With *identical* saved Torch weights `[1,10,32,2048]` and values `[1,10,2048,128]`, Core ML's FP32 product at that element is exactly `8.84375`; Torch's is `8.843749046325684`. These values fall on opposite sides of the BF16 rounding midpoint and reproduce the one-element Q difference. There are 426 raw product differences and one BF16-rounded difference. By contrast, isolated Core ML score matmul and source-exp softmax weights are bitwise exact on the same captured inputs; feeding either Core ML result into the Torch downstream path leaves all rounded outputs exact. The reusable [reference operands](reference.npz) contain q, k, values, scores, masked logits, weights, raw product, and rounded product. [Core ML outputs](outputs.npz) and [probe source](../../../scripts/gpu_long_layer34_isolate.py) preserve the comparison. This diagnoses a shape-dependent Core ML GEMM reduction difference, not a cache or softmax error in this replay.

The [product-layout probes](products/summary.json) show the shape dependency. Keeping all 2048 key slots but presenting only two real query rows makes Core ML's product raw and rounded values bitwise equal to Torch's full-shape reference across the complete output. Cropping to 1026 key slots also makes all BF16 outputs exact, though its raw target differs. A 256-key split gives exact BF16 outputs on this capture, but is not a source-order guarantee. Full-shape einsum and ten per-head matmuls retain the same one-element BF16 failure. The floating-point reduction path therefore depends on GEMM dimensions; merely changing score arithmetic does not fix this case.

The bounded [composed group-8 replay](group8-productrows/summary.json) retains the existing front-padded score-row policy and raw-layout score einsum, then slices softmax weights to the actual input query count *before* the weighted-value matmul. On saved positions `[1024,1025]` and the saved Core ML state, the resulting CPU_ONLY group output matches native Torch bitwise; the prior candidate differs in 543 elements. The [three-token group-8 replay](../tiny3-productrows-group8/summary.json) also matches native Torch bitwise, while the prior candidate differs in 789 elements. Its exact seven-input boundary and native expected output are in the [fixture](../tiny3-productrows-group8/fixture.npz). The experimental *pure Torch* tiny-three graph still differs from native Torch in 789 elements, as did the prior raw-score experiment: the tiny-three claim is specifically about the compiled Core ML result, not general algebraic equivalence.

The shared opt-in integration now exposes `prepare_queries`, `attention_scores`, and `attention_product` hooks in [graphs.py](../../../coreml_port/graphs.py). [dynamic_queries.py](../../../coreml_port/dynamic_queries.py) keeps the tested score geometry and slices weights to actual query rows for the value product. [convert_coreml.py](../../../scripts/convert_coreml.py) selects it with `--queries dynamic-product`; ordinary default behavior remains static. Root's integrated-converter [long](../../04d-cpu/integrated-query-shard/long-replay/results.json) and [tiny](../../04d-cpu/integrated-query-shard/tiny-replay/results.json) group-8 replays are exact. An independently converted integrated [shard-0 package](integrated-shard0/convert-0.json) passed the three canonical prompts (32-token chunks, remainders, and one decode after lengths 44, 58, and 48): all `y` and `tap23_out` outputs are bitwise exact against the original Torch graph [gate record](integrated-shard0/gate.json). The conversion used ordered arithmetic, ordered softmax, source exponential, ordered norm, ordered XSA, lookup GELU, and dynamic-product queries on CPU_ONLY.

This is bounded evidence for the corrected product row geometry at group 8 and canonical shard 0. The complete multi-group/full-model acceptance gate remains separate. Core ML package and source hashes are recorded in the JSON evidence; each experiment wrote a fresh package path. All predictions installed `coreml_port.cleanup_guard` before invoking the pinned Core ML bridge.
