# Source exponential, bounded Core ML validation

Replacing the ordered-attention exponential with `coreml_port.source_exp.exp` eliminates the first observed layer-2 BF16 divergence on canonical prompt 2. The earlier native Core ML exponential yielded 964 differing FP32 softmax weights on identical masked scores; the problematic head/query had 32 of 32 differing weights and caused the attention value to round to 2.546875 instead of Torch's 2.5625. See the [prior diagnostic](../integrated-shard/REPORT.md).

On that exact captured score tensor `[1,10,32,2048]`, the [source-exponential softmax probe](full-softmax/summary.json) produced weights **bitwise identical** to native Torch. The subsequent weighted-value product, using these Core ML weights in Torch, matched all raw FP32 and BF16-rounded values. At the prior failing element, both raw values were 2.5546884536743164 and both rounded values were 2.5625. The source-exponential Torch softmax also matched native Torch bitwise on the same tensor.

The [uninstrumented four-layer shard-0 run](shard0/summary.json) used ordered linear, ordered softmax summation, ordered RMS norm, ordered XSA, and source exponential. It converted a fresh package with the same `norm_divisor` input and 2048-slot state capacity as candidate 2. For all three canonical prompts, each split into a 32-token chunk, remainder, and one decode token, source-exponential Torch and native-exponential corrected Torch outputs were bitwise identical. Core ML CPU_ONLY `y` and `tap23_out` then matched that Torch reference bitwise on **all nine steps**. Conversion took 52.9 seconds. The evidence records script/source hashes and package-file hashes; the package is [here](../../../artifacts/04d-gpu/source-exp/shard0/0.mlpackage).

This validates source exponential on the recorded softmax domain and these prompts. Its implementation is designed for finite, nonpositive softmax arguments and masked negative infinity; it is not established as a general exponential or a guarantee for unseen prompts. This four-layer result does not qualify the full 48-layer candidate. Root is running that separate gate.

The pinned Torch CPU FP32 softmax's real-key-count tail does **not** introduce a new long-context sum-order hazard for 4–2048 keys. It uses four-lane accumulation and a partial vector load with `Vec::set` for 1–3 trailing elements, retaining the other accumulator lanes ([SoftMaxKernel.cpp](../../../sources/torch-2.7-linear/SoftMaxKernel.cpp), lines 113–143; [functional_base.h](../../../sources/torch-2.7-linear/functional_base.h), lines 136–150; [vec128_float_neon.h](../../../sources/torch-2.7-linear/vec128_float_neon.h), lines 163–175). The graph's masked extra slots contribute positive zero to those same lanes. A **three-key short-context exception** exists: Torch's `size<4` scalar path sums `(a+b)+c`, while the fixed 2048-slot graph folds `(a+c)+b` ([functional_base.h](../../../sources/torch-2.7-linear/functional_base.h), lines 11–27). Positive float32 values `a=1`, `b=0.36899313`, `c=0.51139003` yield 1.8803833 versus 1.8803831. The current tiny three-token checkpoint passes at its measured output; this source-level observation does not warrant a correction without a failing gate. See the [detailed tail review](softmax-tail-review.md).

Reproduction scripts: [full-shape softmax](../../../scripts/gpu_source_exp_softmax.py) and [shard 0](../../../scripts/gpu_source_exp_shard.py). Both install `coreml_port.cleanup_guard` before Core ML predictions.
