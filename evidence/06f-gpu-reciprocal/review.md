# Independent 06f review

## Host candidate and native worker review

The reciprocal candidate accepts an explicit denominator and a supplied FP32 reciprocal seed; it does not compute or replace the seed. Its documented input domain is finite positive FP32 `d` in `[0.5, 8]`, with a positive normal seed no more than one representable neighbor from the exact nearest FP32 reciprocal. The host preflight evaluates the Torch helper over the retained prior inputs, adjacent-seed cases, boundary neighborhoods and fixed-seed random inputs. Its recorded result has 31,147 exact corrections, 249,176 exact arithmetic-identity checks, CPU reference preservation, and zero native calls. The input/run archives and recorded source/design pins matched disk when inspected. This qualifies only the tested host helper and exact identities; the separate MIL expression and native backend remain unqualified.

The native worker separates two decisions. C3 compares the direct-MIL `real_div` control against captured same-policy outputs. C3b evaluates the correction with nearest, lower-neighbor, upper-neighbor, and captured GPU seeds independently against the exact oracle. It also checks the diagnostic seed passthrough against the same-attempt control and CPU nearest-seed correction against CPU control bytes. Thus a C3b pass can be recorded even if the small standalone control fails C3 reproduction, but the worker's overall `passed` remains false and its decision forbids a repair claim until an in-model group gate. The model uses separate control/correction programs with a shared dynamic query symbol; operation counts and serialized operation hashes are recorded, and correction is required to contain no `real_div` or `inverse`. Calls compare all inputs for preservation, require the `value` output, and the final guard requires 36 native prediction calls.

This is a read-only static review. No model conversion, compilation, loading, or prediction was performed by this review. The native result must keep compute policy distinct from verified physical device placement; the later raw-result audit independently checks the frozen pins and artifacts.

## Native-1 raw-result audit

I independently checked the frozen `native-1-protocol.json`, 36 call archives, 28 seed-case archives, and both compiled/package inventories. Protocol and result hashes agree; all listed protocol/result pins and saved archive hashes match disk. Raw correction outputs are finite FP32 and bitwise equal to the rational-oracle reference for all 28 correction calls across CPU and CPU_AND_GPU, including nearest, lower, upper, and captured-GPU seeds. The four CPU nearest-seed results are also byte-identical to the same-attempt CPU `real_div` control. All eight controls match the exact rational reference, all 36 calls preserve their input arrays, and the recorded guard is 0 state / 36 plain / 36 GIL releases.

The original C3 reproduction gate remains false. I directly compared the standalone controls with saved group `var_5675`: both CPU cases reproduce exactly; the warm CPU_AND_GPU control differs at 3 elements (first `[0,1,0]`, bits `0x3ebe1c0d` vs saved `0x3ebe1c0e`); the cold CPU_AND_GPU control differs at 11 elements (first `[0,0,0]`, bits `0x3f08f0cf` vs saved `0x3f08f0d0`). Thus C3b's external-seed component qualification passed while C3 did not reproduce the saved GPU behavior. The result correctly reports `passed=false` and requires a separate in-model diagnostic; it does not establish a group repair. Physical device placement remains unverified.

The two candidate CPU endpoint/state sets match the original CPU baseline byte-for-byte. The guard records 0 plain / 12 state / 12 GIL releases.

I recomputed the corrected `var_5675` arrays from each saved tapped denominator with the exact rational oracle; all four arrays match bitwise, and every seed is within one FP32 neighbor of the oracle result with denominators inside `[0.5,8]`. On the warm chunk, all 12 tapped normalization stages match the prior CPU arrays under CPU_AND_GPU. The cold CPU_AND_GPU normalization still differs upstream and is retained as a separate trajectory.

The group GPU endpoint change is local and incomplete: cold candidate GPU `y` and all eight states are exactly unchanged from the original GPU candidate. Warm candidate GPU `y` relative RMSE to original CPU falls from `0.002101810576` to `0.000730509861` (65.24% reduction), while differing `y` elements fall from 4,451 to 2,980 and maximum absolute error from 1,024 to 128. Across all cache elements, GPU-versus-CPU state differences fall from 2,217 to 379; the candidate remains non-exact. These are two fixed-chunk diagnostics, not a full-model pass or performance result. The group replay demonstrates the local warm correction in the supplied fixture despite failed standalone C3 reproduction; it does not prove general group behavior or physical GPU placement.
