## Finding

## Concrete coverage gaps and false-confidence risks

- **Stale or unintended packages (high):** `Pipeline.__init__` loads only `artifacts/04-coreml/model`. The ordered conversion commands can target `artifacts/04c-precision/ordered`, but no selection argument or package-manifest check connects that output to the runner. Evidence could therefore describe an experimental conversion while tests still exercise old packages. The recorded `04c` summary confirms this is the current state.
- **Diagnostic graph fusion (high):** `probe_coreml_layer_stages.py` exports many intermediate outputs to locate the first divergence. Its own docstring warns that diagnostics can affect fusion. Those measurements are diagnostic only; the final candidate must pass with the ordinary graph outputs and original end-to-end validator.
- **Missing Core ML window/cache boundary coverage (high):** the portable acceptance contract explicitly calls for 1024/1025 local-window boundaries, global-key retention, chunked prefill, and single-token positions. `validate_coreml.py` checks canonical prompts and four teacher-forced decode steps, but not this boundary sequence. Prior Core ML boundary evidence failed (max score errors 0.41047 at 1024 and 0.64559 at 1025), so it must be repeated against the selected corrected candidate.
- **Long prefill is only a finiteness check (high):** prior long-prefill results cover lengths through 2048 for finite output, not score agreement with the reference. Numerical parity at supported capacity remains unproven.
- **Generation stop mismatch (medium/high):** the published model EOS is 151645 while tokenizer EOS is 151643. Current Core ML `generate` stops on the published ID and optionally takes the tokenizer ID via explicit `extra_stops`; the recorded successful sample uses the explicit stop. That proves a usable caller-selected stop policy, not that the published stop behavior matches generated sequences. Preserve incomplete status on length exhaustion.
- **Reference scope (high, qualification boundary):** the qualified reference is an exact local implementation/checkpoint comparison, not an independently captured original CUDA/vLLM oracle. A complete CPU gate pass supports “matches qualified local CPU reference” only; the independent-runtime gate remains blocked.
- **Coverage of decoded continuation (medium):** the existing Core ML validator teacher-forces four tokens per canonical prompt and samples an extra stop after one generated token. This is useful mechanics coverage but too short to substantiate long continuation parity or stop behavior. Use the frozen continuation fixture and preserve exact prefixes across all compared steps.
- **No clean-install claim (medium):** current evidence explicitly says clean-machine installation is untested. Keep this outside the CPU numerical milestone unless packaging is included in the acceptance claim.

## Source exponential qualification

Extended the owned Torch audit to replace only `ordered_attention.exponential` with `source_exp.exp`, retaining candidate-2 ordered linear, softmax summation, norm, XSA, and GELU. The new run again used all three canonical prompts, chunked prefill in a persistent 2048-slot FP16 cache, selected hidden checks, and four reference-matched decode steps per prompt.

Evidence and all source digests are in [source-exp result JSON](torch-candidate/candidate2-sourceexp-canonical3/results.json). This closes the short canonical Torch question for the full source-exponential injection set; Core ML conversion/runtime remains independently gated.

`source_exp.exp` is explicitly bounded to finite nonpositive softmax deltas and masked negative infinity. The softmax path first subtracts the row maximum, so finite entries are nonpositive; causal attention rows retain at least their current key, while masked `-inf` is mapped to zero by the final `where`. The implementation clamps the polynomial path to [-104, 0], which covers normal/subnormal softmax mass through underflow to zero. Its exponent range reduction indexes remain within the `2**[-80..0]` table for q from -150 through 0. Existing evidence `evidence/04d-cpu/sleef-exp-2/summary.json` records exact agreement with Torch `exp` for 30,245 captured/random domain values, and this full Torch model audit confirms exact end-to-end behavior on the canonical cases. Nonpositive finite values and masked `-inf` are the supported domain; positive inputs and NaNs are not supported, and the FMA helper materializes scalar constants on CPU, so this should not be treated as a general device-agnostic exponential primitive.

Root subsequently recorded an independent fresh-input Core ML exponential suite with 540,672 exact values across zeros, post-conversion uniform/loguniform samples, and boundaries: `evidence/04d-cpu/source-exp-independent-1/summary.json`. Sol also reported that the previously failing full-shape softmax weights and value product now match exactly in isolation; the composed shard gate remains the next boundary to assess.

## Opt-in tiny-prefix request warmup adapter

Its ordinary `Pipeline` superclass and default route are unchanged. It records only the owned token IDs while request length is below 16. If a later call begins at lengths 1–15, it replays `warmup_ids + new_ids` through fresh states; the original request’s states and history are published only after a complete forward and head score. It trims tap callbacks to only new token positions across any 32-token boundaries, clears token history at length 16, and invalidates the original plus closes/clears fresh state on any warmup exception. Request close clears both Core ML states and saved IDs.

API for integration: construct `TinyPrefixPipeline("CPU_ONLY", model_dir, identity_manifest)` using the same explicit candidate path/manifest as the ordinary runner, then use `request()`, `forward(ids, request, capture=None)`, and `request.close()` with the existing API.
